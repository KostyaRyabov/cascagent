# ADR-001: Выбор inference-движка (llama.cpp; кандидат ExLlamaV2/TabbyAPI)

- Статус: **Accepted** (для llama.cpp) / **Proposed** (переход на TabbyAPI — не принят)
- Дата: 2026-10-09
- Контекст расширен в: `docs/stack.md`, AGENTS.md §3, §9

## Контекст

Целевое железо: 4 GB VRAM. Нужен OpenAI-совместимый сервер с изолированными
вызовами агентов, предсказуемым KV-кэшем и минимальным overhead.

Эволюция попыток:
1. **Ollama** — простота, но: обвязка модели-менеджера, нестабильный prefix
   cache, нет ручного save/restore KV, полноразмерный f16 KV-кэш.
2. **llama.cpp server** — ручной `/slots/N?action=save|restore`, flash-attn,
   квантованный KV (`--cache-type-k q8_0`), но GGUF Q4_K_M для 8B = ~5.5 GB
   (не влезает), значит модель ограничена 4B классом.
3. **ExLlamaV2 + TabbyAPI** — EXL2 4.0bpw даёт Qwen3 8B ≈ 4.2 GB (влезает),
   draft model, но нет save/restore KV (только авто prefix cache), Python-env
   зависимости, вне текущего списка «не делать» (AGENTS.md §9).

## Решение

Действующее решение: **llama.cpp server + Qwen3 4B Q4_K_M**. Код пишется под
его интерфейс; абстракция `client.chat(use_think=...)` скрывает различия API.

Кандидат на ревизию (зафиксирован как Proposed): TabbyAPI + Qwen3 8B EXL2
4.0bpw. Критерий принятия: доля ложных атомов/битого вывода 4B из
history.jsonl >= 5% после Этапа 3 (stack §7). При переходе `cache_manager.py`
деградирует до no-op, остальной CPU-слой не меняется (инварианты интерфейса —
stack §4.3).

## Последствия

- (+) Гарантированный save/restore KV -> персистентность префиксов между запусками.
- (+) Минимальные зависимости, один бинарник.
- (-) Качество рассуждений 4B ниже 8B; риск передекомпозиций компенсируется
  think-режимом на L0-L2 и degenerate-правилом (CPU).
- (-) Скорость генерации ниже потенциала EXL2-draft; осознанно принято
  («качество рассуждений критичнее скорости»).
