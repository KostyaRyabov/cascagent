# ADR 005: Переименование ConflictResolver → Orchestrator; привязка агента после PrePlugin

Дата: 2026-10-13
Статус: принят
Уточняет: ролевые модели v4/v5 (product §4), заменяет их v6.

## Контекст

1. В v5 роль оркестратора неатомных уровней была названа `ConflictResolverAgent`.
   Выяснилось, что штатная работа на неатомном уровне — это не про конфликты,
   а про оркестрацию (декомпозиция → ожидание детей → подтверждение/редекомпозиция).
   Имя размывалось.
2. Обнаружен сбой декомпозиции: Decomposer может сначала пометить задачу как
   неатомную, а в процессе декомпозиции понять, что задача фактически атомарна
   (выдала `<atom>` или одного идентичного родителя ребёнка — degenerate-цикл).
   В этом случае задачу должен выполнять Executor, а не оркестратор.
3. Оркестратор задумывался как вызов Decomposer через PrePlugin
   (`agent-as-tool`). Тогда возникает вопрос: когда фиксируется роль агента?

## Решение

### 1. Переименование
`ConflictResolverAgent` → **`OrchestratorAgent`** (модуль `orchestrator.py`).
Оркестратор одинаково работает на всех уровнях декомпозиции:
- штатно — выполняет НЕатомные задачи как оркестратор своего уровня;
- аварийно — разрешает тупики нижних уровней (FAILED после retry/reflect,
  зацикливание, противоречия sibling-результатов — roadmap #20).

### 2. Привязка агента (role binding) — ПОСЛЕ PrePlugin
Этап ENRICHMENT разбивается на два шага (process §1.1):

```
PENDING → ENRICHMENT:
  1) PrePlugin-секция (в т.ч. DecomposeTool как agent-as-tool) —
     собирает факты: atom-флаг от Decomposer, enriched context, recall/RAG;
  2) CPU-диспетчер выбирает исполнителя по фактам PrePlugin'ов;
→ RUNNING(выбранный агент)
```

Правило выбора (детерминированное, CPU — принципы principles §2.1 не нарушаются):

| Факт после PrePlugin | Агент |
|---|---|
| `is_atom=True` (в т.ч. «сбой» Decomposer: `<atom>` или degenerate-ребёнок) | **Executor** |
| `is_atom=False`, есть дети | **Orchestrator** (экземпляр на уровень) |
| FAILED после retry/reflect, зацикливание, contradictory siblings | **Orchestrator** (аварийный режим: редекомпозиция / ask) |

### 3. «Сбой» Decomposer — это не сбой, а штатный путь
Decomposer остаётся PrePlugin-инструментом. Его вывод — только факт для
диспетчера. Смена роли не требует пересоздания задачи: Kanban-задача едина,
меняется только выбор агента перед RUNNING. Идемпотентность: если Decomposer
уже вернул `<atom>`, повторный вызов декомпозиции не происходит (ленивость, ADR 004).

### 4. Пользовательские агенты
Пользователь может декларировать своих агентов и правила вызова
(кто кого зовёт как MCP tool); диспетчер подчиняется тем же правилам:
роль привязывается после PrePlugin на основе объявленных триггеров.

## Последствия
- Рекурсия чистая: Orchestrator уровня N порождает детей; каждый неатомный
  ребёнок получает свой экземпляр Orchestrator; атомы уходят к Executor.
- `executor.py` остаётся единственным местом выполнения атомов;
  суммаризация результатов детей — компетенция Orchestrator (зовёт Summarizer).
- Documented in: product §4–5 (v6 + mermaid), process §1.1, plugins §agent-as-tool,
  roadmap #20.

## Дополнение (2026-10-13): диспетчеризация — часть внутреннего цикла агента

**Решение:** `Agent` объединяет «обычный цикл» и диспетчеризацию: это не
промпт + MCP tools, а полный конвейер PENDING → ENRICHMENT(Pre + выбор
роли) → RUNNING(run) → оценка(Post/Validator). Внешний рекурсивный
`execute_task` (эталон v2) заменён тонким циклом `dispatch_loop`
(process §1.2): рекурсия дерева выражена очередью задач + park/wake
родителя, а не Python-стеком.

Пункты:
1. Каждый агент имеет **локальный набор задач** (дети его уровня) — как
   view над единым Kanban-persistence (`parent_id`); одной общей
   in-memory структуры не требуется.
2. Механизм выбора роли из п.2 этого ADR получает API-форму:
   `Agent(role="auto")` → Pre-секция → `pick_role(local_memory)` →
   `bind_body(role)` → RUNNING. Смены роли внутри run() нет.
3. CPU-диспетчер не упразднён — он живёт внутри каждого агента как
   детерминированная обвязка этапов; границы «когда/кем vs что» не меняются.
4. Оценка выполнения — этап PostPlugin (Validator): DONE только при
   `action == "accept"`; reject → FAILED → эскалация родителю-Orchestrator.

Spec: process §1.1–1.3 (таблица этапов, dispatch_loop, mermaid),
plugins §6.4 (примечание).
