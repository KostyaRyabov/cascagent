# ADR-004: Ленивая декомпозиция (дерево строится по мере выполнения)

- Статус: **Accepted**
- Дата: 2026-10-10
- Расширено в: `docs/process.md` §1 (эталонный execute_task),
  `docs/protocol.md` §7, `docs/examples.md` §2; принципы — AGENTS.md §4, §7.

## Контекст

Классические planning-системы строят полное дерево задач заранее, затем
исполняют листья. Альтернатива — декомпозировать узел только в момент,
когда он начинает исполняться. Ограничения проекта: одна локальная модель
на 4 GB VRAM, 10–20 с на вызов, бюджет контекста ~8k токенов.

## Решение

**Ленивая декомпозиция:** каждый узел декомпозируется ровно один раз —
непосредственно перед исполнением его детей, на актуальном обогащённом
контексте (результаты DONE-siblings уже в промпте).

Аргументы:
1. Контекст растёт по мере выполнения — ранняя декомпозиция работает на
   предположениях, поздняя видит реальность (файлы, версии, ошибки).
2. Провал/смена подхода в 0.1 делает ветки 0.2+ потенциально бессмысленными;
   при ленивой схеме они просто не разлагаются — экономия токенов и времени.
3. Экономия LLM-вызовов прямо бьёт по главному лимиту системы (cpu-offload §0:
   дерево 30 узлов × 2 вызова = часы машинного времени).
4. Качество декомпозиций выше: enricher передаёт проверенные факты вместо
   гипотез (ADR-002 минимализм промпта рассчитан именно на это).

## Последствия

- (+) Нет вызовов на отменённые/несостоявшиеся ветки.
- (+) Results «стекают» вверх естественным порядком рекурсии; resume после
      краша бесплатен (DONE-узлы читаются из Kanban без инференса).
- (-) Нет общего обзора плана заранее — пользователь видит дерево лишь
      по мере роста; CLI рендерит частичное дерево (examples.md §5 anti-пример
      «разбита заранее» запрещён).
- (-) Сложнее оптимизировать параллельное выполнение siblings — сейчас
      несуществующая проблема: single-flight очередь (product §5); при
      переходе на параллелизм порядок-как-зависимости придётся пересмотреть.
- (-) Reflect не может «переписать план» списком задач — контракт reframe
      одной задачи (process.md §6); планирование графа остаётся на CPU.
