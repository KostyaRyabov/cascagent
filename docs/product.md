# cascagent — Продукт: видение, функции, пользовательские сценарии

> Статус: **draft v1** (для обсуждения; после принятия фиксировать решения
> сюда и в AGENTS.md). Протокол общения с LLM — `docs/protocol.md`,
> архитектура модулей — `docs/architecture.md`, стек инференса —
> `docs/stack.md`, реестр CPU-алгоритмов — `docs/cpu-offload.md`.

## 1. Миссия, философия и позиционирование

### 1.1 Основная идея

Ключевая философская установка проекта:

> **LLM занимается ТОЛЬКО семантикой и рассуждениями. Всё остальное —
> маршрутизация, поиск инструментов, валидация, управление памятью,
> проверка формата, исправление опечаток — детерминированные CPU-алгоритмы.**

Наблюдения, из которых это выросло:
1. Малые модели (4B–8B) плохо работают с форматом: нарушают JSON-схемы,
   галлюцинируют структуру → наш протокол v2 сознательно plain-text.
2. Модели не нужна память системы (Kanban, список инструментов, история
   всех агентов) — это работа CPU.
3. Простые операции (поиск по словарю, опечатка, проверка прав) CPU делает
   за микросекунды; просить LLM — расточительство.
4. Каждый токен контекста дорог на 4 GB VRAM: нельзя класть в промпт
   схемы 1000 MCP-инструментов (50k+ токенов).

Полный реестр «что на CPU» — `docs/cpu-offload.md`; что остаётся на GPU
(ровно 5 видов вызовов) — там же §3.

### 1.2 Название и символизм

**cascagent = casc(ade) + agent.** Задачи делятся на подзадачи *по мере
выполнения*, а не заранее; каждая получает контекст от выполненных
siblings; результаты «стекают» вверх, формируя result родителя — как
водопад: вода течёт сверху вниз, информация о выполнении поднимается снизу
вверх. Альтернативы отклонены: `fractal-agent` (занято), `bonsai`
(менее техническая метафора), `liteAgent` (слишком общее).

### 1.3 Лицензия: Apache 2.0

Обоснование: патентная защита (контрибьюторы дают патентную лицензию
автоматически); совместимость со стеком (Qwen3, HuggingFace — Apache 2.0);
доверие компаний-контрибьюторов; свободное коммерческое использование;
стандарт индустрии (Kubernetes, TensorFlow, PyTorch). Рассматривались
MIT (нет патентной защиты), GPL 3.0 (copyleft отпугивает коммерческих),
dual licensing (избыточно). Файлы: `LICENSE` (текст), `NOTICE`
(атрибуции ExLlamaV2/Qwen3/TabbyAPI), в каждом `.py` — заголовок
`# SPDX-License-Identifier: Apache-2.0`.

### 1.4 Позиционирование

**cascagent** — это CLI-оркестатор, который берёт сложную задачу пользователя
и автономно доводит её до результата на **слабом железе** (4 GB VRAM /
16 GB RAM) с одной локальной моделью (Qwen3 4B Q4_K_M через llama.cpp).

Ключевая идея: маленькая модель не умеет держать длинный контекст и сложный
протокол — но умеет хорошо делать **один маленький семантический шаг**.
Система превращает её в «вычислительное ядро» для атомарных операций,
а всю инженерию (планирование, память, валидацию, состояние) выполняет
детерминированный CPU-слой.

### Целевые пользователи
- Разработчики/энтузиасты без доступа к облачным LLM (приватность, цена, оффлайн).
- Исследователи агентных систем — cascagent как полигон «много агентов на одной слабой модели».
- Автоматизация рутинных пайплайнов на домашнем сервере / ноутбуке.

### Чем НЕ является (границы продукта, anti-scope)
- Не IDE-ассистент с инлайновых автодополнением.
- Не чат-бот общего назначения (нет свободной беседы).
- Не замена CI/CD: код запускается песочно и ради задачи, а не для прода.
- Не мульти-модельный стек (одна модель — принципиальное решение, AGENTS.md §9).

## 2. Архитектурные принципы (детально)

> Сжатая версия — AGENTS.md §2; здесь — обоснование, анти-паттерны и
> количественные эффекты. Числа в таблице §2.2 — порядок величин для
> capacity planning, не бенчмарк.

### 2.1 Изоляция агентов

**Принцип:** каждый агент работает в полностью изолированной сессии с
минимально необходимым контекстом. На практике: каждый вызов LLM —
отдельный HTTP-запрос (не продолжение чата); агент получает только свою
задачу + минимум контекста родителя + обогащённые данные; общей памяти
между агентами нет — утечки контекста физически невозможны.

Почему это важно:
1. **Предсказуемое потребление VRAM** — точно знаем стоимость каждого агента.
2. **Нет переполнения контекстного окна** — агент не страдает от того, что
   50 других агентов написали в общую историю.
3. **Параллелизм без конфликтов** (когда появится; сейчас single-flight).
4. **Лёгкая отладка** — каждый агент изолирован, тестируется отдельно.
5. **Воспроизводимость** — один и тот же запрос даёт тот же результат
   (temperature=0.2).

Анти-паттерн (общий чат всех агентов):
```
User: задача 1 → Agent1: результат 1
Agent2: я видел результат 1, сделаю задачу 2...   ← контекст загрязнён
Agent3: я видел 1 и 2, сделаю задачу 3...         ← ещё больше мусора
```

Правильный подход (stateless агенты + Kanban как единственный канал):
```
Agent1: [свой контекст]                      → результат 1
Agent2: [свой контекст + результат 1 из Kanban] → результат 2
Agent3: [свой контекст + результаты 1,2 из Kanban] → результат 3
```

### 2.2 Минимизация контекста

**Принцип:** каждый токен в контексте стоит VRAM и времени префилла.

Экономия токенов через CPU-алгоритмы:

| Задача | Если делает LLM | Если делает CPU | Экономия |
|--------|-----------------|-----------------|----------|
| Выбор инструмента из 1000 | 50 000 токенов (все схемы) | 0 (агент пишет `read_file path.txt`) | 50 000 |
| Исправление опечатки `read_fiel` | ~200 токенов (рассуждения) | 0 (Левенштейн за 0.1 мс) | 200 |
| Поиск в документации | 5 000 токенов (вся дока) | 500 (RAG top-3 релевантных фрагментов) | 4 500 |
| Валидация формата | 1 000 токенов (схема + проверка) | 0 (CPU-парсер) | 1 000 |

Итого: вместо ~60 000 токенов → ~1 000. Это позволяет работать с малыми
контекстными окнами (4–8k) и малыми моделями. Реестр механизмов —
cpu-offload P1–P9.

### 2.3 Перенос логики на CPU

**Философия:** «если задачу можно решить детерминированным алгоритмом —
LLM её НЕ решает» (критерий и полный реестр — cpu-offload §1–2).

| Задача | Решение на CPU | Почему не LLM |
|--------|----------------|---------------|
| Выбор инструмента из 1000 | BK-tree по запросу агента | LLM не должна видеть 1000 MCP-схем |
| Исправление опечаток | Левенштейн + фонетика (`fix_typo`) | LLM тратит токены на рассуждения |
| Поиск похожих задач | эмбеддинги + cosine similarity | у LLM нет долгосрочной памяти |
| Поиск в документации | RAG (BM25 + vector search) | LLM галлюцинирует факты из документации |
| Валидация формата | парсер отступов + sanitize | LLM нарушает JSON-схемы |
| Состояние задач | SQLite Kanban | LLM не может надёжно помнить состояние |
| Зависимости/планирование | граф в SQLite, FIFO-очередь | детерминированная топосортировка |
| Кэширование результатов | exact-match + semantic кэш | LLM не должна помнить прошлые вызовы |
| Суммаризация выводов | CPU-конкатенация; LLM-summarize — только при превышении budget | изолированный редкий вызов, не рабочий контекст |

### 2.4 Минимальный формат для LLM

Модель отвечает **простым текстом**, не JSON; структуры парсятся на CPU.

Плохо (модель думает о формате):
```json
{"tool": "read_file", "parameters": {"path": "/home/user/data.txt"}}
```
Риски: забытые кавычки, перепутанные поля, лишние поля, невалидный JSON —
на исправление уходят ретраи с новой генерацией.

Хорошо (модель говорит что хочет):
```
read_file /home/user/data.txt
```
CPU: парсит строку → BK-tree находит `read_file` даже при опечатке
`read_fiel` → формирует структуру → валидирует параметры.

Для декомпозиции — тот же принцип: `Название` без отступа +
`    Описание` с отступом; парсинг ~20 строк кода (protocol §3).

### 2.5 Пользовательские сценарии (краткий обзор)

| # | Сценарий | Что делает система | Роль LLM |
|---|----------|--------------------|----------|
| S1 | Декомпозиция: `cascagent --query "..."` | Дерево задач до атомов, Kanban, статистика токенов/времени | Только декомпозиция (короткие промпты ~200 симв.) |
| S2 | Полное выполнение: `--run` | Рекурсивное выполнение атомов, сборка результатов вверх по дереву | Декомпозиция + выполнение атомов + рефлексия при сбоях |
| S3 | Наблюдение: `cascagent status / tree / log` | Рендер дерева, статусов, счётчиков из SQLite/JSONL | — (чистый CPU) |
| S4 | Пауза/возобновление | Персистентный Kanban: процесс можно убить и продолжить (`--resume <task-id>`) | — |
| S5 | Передекомпозиция сбоя | ReflectAgent → новая версия задачи → повторная декомпозиция | Анализ провала, альтернативный план |
| S6 | Обучение системы | После каждой решённой пары (brief, result) — запись в semantic memory; будущие обогащения контекста используют recall | — (эмбеддинги — отдельная лёгкая модель или та же, batch=1) |
| S7 | Документация/знания | RAG по подключённым корпусам (`--docs ./dir`), фрагменты попадают в `Контекст:` | — |

## 3. Функциональные возможности (что умеет продукт)

### 3.1 Ядро (Этапы 1–3)
- Рекурсивная декомпозиция произвольной текстовой задачи до атомов (`<atom>`).
- Защита от вырожденных ответов (повтор родителя = атом, protocol §3.6).
- Дедупликация подзадач (SequenceMatcher ≥ 0.75), запрет циклов по предкам.
- SQLite Kanban: pending/running/done/failed, parent_id, порядок = зависимости.
- JSONL-история каждого LLM-вызова (prompt, think, final_response, timings)
  + человекочитаемый debug.log.
- CLI: запуск, дерево, статус, экспорт Markdown-отчёта.

### 3.2 Исполнение (Этап 4+)
- TaskExecutor: выполняет атом детерминированными инструментами
  (файловые операции, shell, python-сниппеты, сетевые GET) либо одним
  изолированным LLM-вызовом («чистая генерация текста»).
- Sandbox: рабочая директория проекта + allowlist инструментов; destructive
  операции (rm, git push, sudo) — только после подтверждения человеком
  (`--auto-approve off|safe|all`).
- Retry policy: 1 автоматический retry → ReflectAgent → re-decomposition →
  максимум N=2 попытки, далее FAILED с накопленным diagnosis.

### 3.3 Память и обогащение (Этап 4–5)
- SemanticMemory: remember(brief, result) / recall(query, top_k=3).
- ContextEnricher: RAG(BM25+vectors) + recall + чеклист siblings +
  Selective Context (сжатие длинных выводов до budget'а).
- BK-tree: выбор инструмента/имени из каталога за O(log n) + fix_typo.

### 3.4 Отчётность
- По завершении: результат корневой задачи, дерево со статусами,
  метрики (число вызовов, токены, время, доля atom-vs-split, cache hit rate).

## 4. Системные агенты

Принцип: **агент = роль + isolated prompt + жёсткий контракт ввода/вывода**.
Все агенты вызывают одну и ту же модель, но никогда не видят чужой контекст.
Обвязка (маршрутизация, валидация, хранение) — CPU.

| Агент | Модуль | Триггер | Вход | Выход (контракт) | Кто вызывает |
|-------|--------|---------|------|------------------|--------------|
| **DecomposerAgent** | `decomposer.py` | задача не атом, есть дети-кандидаты отсутствуют | brief + enriched context + siblings-checklist | список `Название/    Описание` или `<atom>` | Оркестратор |
| **ExecutorAgent** | `executor.py` | задача — атом | brief + description + контекст родителя (≤ budget) | текст результата (или ошибка с кодом) | Оркестратор |
| **ReflectAgent** | `reflector.py` | FAILED атома или degenerate-цикл декомпозиции | brief + description + result/error + trace статуса | JSON-lite: `причина` + `предложение` (переформулировка задачи) | Оркестратор (после retry) |
| **ResearchAgent** | `researcher.py` | enrichment не нашёл ничего релевантного (recall/RAG пусты) | вопрос (brief) | краткая сводка фактов ≤ K токенов | Enricher через оркестратор |
| **SummarizerAgent** | `executor.py` | children done, результат > budget | конкатенация детских results | сжатые выводы для `parent.result` | Оркестратор |
| **ValidatorAgent** | ⬜ план (опц.) | сомнительные результаты Executor | задача + результат | pass/fail + причина | Оркестратор |

Важно: DecomposerAgent — единственный агент, чей формат строго регламентирован
(protocol §2–3). Остальные агенты отвечают свободным текстом в пределах
output-budget; их промпты короткие и фиксируются константами в своих модулях.

**Что агенты НЕ делают:** не выбирают друг друга (роутит CPU-оркестратор),
не пишут в Kanban напрямую (пишет оркестратор после валидации), не хранят
состояние между вызовами (stateless; состояние — только в задаче и памяти).

## 5. Жизненный цикл задачи (state machine)

```
PENDING ──(decompose)──► разбита? ──да──► ДЕТИ в Kanban, родитель ждёт детей
   │                        │нет(<atom>)
   ▼                        ▼
 RUNNING(атом) ──ok──► DONE ──► summarize_results() вверх по дереву
   │ failed
   ▼
 RETRY(1x) ──ok──► DONE
   │ failed
   ▼
 ReflectAgent ──► reframe(brief', description') ──► PENDING (depth+1, max 2 цикла)
   │ не помогло
   ▼
 FAILED (diagnosis сохраняется, ветка помечена, root получает частичный результат)
```

Инварианты:
- Родитель становится DONE только когда все дети DONE (или ветка осознанно
  признана FAILED с `partial=true` в результате).
- Никаких параллельных LLM-вызовов (single-flight): очередь FIFO по Kanban —
  железо позволяет один инференс одновременно.

## 6. Точка расширения: инструменты Executor

Каталог инструментов — YAML-манифесты (`tools/*.yaml`: имя, описание, аргументы,
risk level). Выбор инструмента для атома — CPU: BK-tree по описанию задачи
→ топ-3 кандидата → в промпт Executor попадает только подпись выбранного
инструмента (не схема!). Это реализация AGENTS.md §2.3 «выбор из 1000 за O(log n)».

## 7. Метрики успеха продукта

- % задач, доведённых до DONE на железе 4GB VRAM без OOM.
- Среднее число LLM-вызовов на задачу и среднее время (таргет: декомпозиция
  одного узла < 15 s на i5 + RTX 3050).
- Cache hit rate префиксного KV-кэша (SYSTEM_PROMPT) — таргет > 80%.
- Доля ложных атомов (задача объявлена атомом, но не выполнена) — таргет < 5%,
  снижается через refine протокола, а не эвристики.
