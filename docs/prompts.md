# cascagent — Системные промпты и форматы общения с LLM

> Статус: **проект v2**. Системный промпт декомposer'а зафиксирован
> дословно в `parser.SYSTEM_PROMPT` и в `docs/protocol.md` §2 — менять
> текст можно только вместе с тестами. Этот документ собирает промпты
> всех агентов, разбор вывода и обработку ошибок в одном месте.

## 1. Философия минимализма

Модель должна знать **как можно меньше** о системе.

Что модель ЗНАЕТ: что такое «задача», что есть «контекст», что нужно
разбить задачу на подзадачи, что если не делится — пишет `<atom>`.

Что модель НЕ ЗНАЕТ: RAG, semantic memory, BK-tree, Kanban, SQLite,
JSONL, других агентов и их состояние, категории (удалены в v2),
обогащение контекста, Reflect/Research агентов.

Зачем:
1. меньше промпт → меньше токенов → быстрее префилл;
2. меньше информации → меньше путаницы → стабильнее вывод малой модели;
3. модель не пытается «играть» с системой — решает свою семантическую задачу;
4. архитектуру вокруг модели можно менять, не трогая промпт (и KV-кэш префикса).

## 2. Системный промпт декомposer'а (фиксируем дословно)

```
Разбей задачу на подзадачи следующего уровня детализации.

КАЖДАЯ ПОДЗАДАЧА:
Название задачи
    Подробное описание что нужно сделать

ПРАВИЛА:
- Подзадачи должны полностью покрывать исходную задачу
- Каждая подзадача — конкретное действие
- Не повторяй исходную задачу
- Если задача не делится — напиши только: <atom>
```

~200 символов (~50 токенов). Эволюция версий:

| Версия | Размер | Что убрано |
|--------|--------|-----------|
| v1 (категории `> ! ? ⚛`) | ~800 токенов | — |
| v2a (с примерами) | ~400 токенов | категории |
| **v3 финал (этот)** | **~50 токенов** | примеры (формат задан структурой «КАЖДАЯ ПОДЗАДАЧА») |

Экономия: (800 − 50) × 100 вызовов ≈ 75 000 токенов только на system
префиксе; плюс префикс стабилен → llama.cpp prefix caching / KV save-restore
бьёт по нему бесплатно (stack §6).

## 3. Структура пользовательского промпта

Собирается референсной pure-функцией `parser.build_user_prompt(brief,
context_lines, completed_siblings)` (protocol §5):

```
Задача: {task.brief}

Контекст:
{enriched_context.to_prompt_block()}   # собран CPU, источники скрыты

Выполненные ранее:
✓ {sibling.brief}: {sibling.result[:100]}

РАЗБЕЙ НА ПОДЗАДАЧИ:
```

Пример полного вызова (декомпозиция JWT-аутентификации):

```
SYSTEM:
[§2, ~50 токенов]

USER:
Задача: Реализовать JWT аутентификацию

Контекст:
Документация:
- FastAPI использует Depends для инъекции зависимостей
- JWT токены обычно хранятся в заголовке Authorization: Bearer <token>

Похожий опыт:
- В проекте blog-api использовался PyJWT с HS256 и секретом из .env

Выполненные ранее:
✓ Создать модель User: Создана модель с полями id, email, password_hash
✓ Настроить Redis: Redis доступен на localhost:6379

РАЗБЕЙ НА ПОДЗАДАЧИ:
```

Типичный размер USER-части: 250–400 токенов (лимит обогащения
`enrichment.max_context_tokens = 500`, data.md §6).

## 4. Формат вывода и парсинг

Правила (детерминированные, protocol §3):
1. строка **без отступа** = brief новой подзадачи;
2. строка **с отступом** (пробелы/табы) = продолжение description;
3. ровно `<atom>` = задача не делится;
4. пустые строки игнорируются.

Пример ответа модели:

```
Создать утилиту для JWT токенов
    Написать модуль auth/jwt.py с create_access_token / create_refresh_token.
    PyJWT, HS256. Access — 15 минут, refresh — 7 дней.

Создать endpoint регистрации
    POST /auth/register: email + password, bcrypt-хэш, создать User, вернуть user_id.
```

Парсинг — `parse_decomposition()` (~20 строк, O(n)):

```python
def parse_decomposition(response: str) -> list[dict]:
    if response.strip() == "<atom>":
        return []
    tasks, brief, desc = [], None, []
    for line in response.split("\n"):
        s = line.strip()
        if not s:
            continue
        if line and line[0].isspace():          # описание текущей
            if brief is not None:
                desc.append(s)
        else:                                    # новая задача
            if brief is not None:
                tasks.append({"brief": brief, "description": " ".join(desc)})
            brief, desc = s, []
    if brief is not None:
        tasks.append({"brief": brief, "description": " ".join(desc)})
    return tasks
```

Обработка краёв (все шаги — CPU, без ретраев «на авось»):
- пустой final_response → трактока как атом (логируется);
- одна подзадача с brief ≈ родителя → degenerate-repeat правило → атом
  (protocol §3.6, cpu-offload A5);
- ответ «совсем не то» (не парсится структура/покрытие) → ReflectAgent
  анализирует провал (product §4), оркестратор решает retry/переформулировку.

### 4.1. Разделение THINK / FINAL (`split_think_and_response`)

Эталон поведения (Глава VI.5 полной документации): нет think-блоков →
`("", text)`; один блок; несколько блоков; **незакрытый блок** (генерация
оборвана на лимите токенов) — хвост после открывающего тега считается
незавершённым рассуждением, final пуст → ретрай по правилам cpu-offload §2.3.

Референс — `src/cascagent/parser.py::split_think_and_response` (реализован,
тесты зелёные); поведение зафиксировано снапшот-тестами:

```python
def test_split_no_think():
    t, f = split_think_and_response("Задача\n    Описание")
    assert t == "" and "Задача" in f

def test_split_with_think():
    t, f = split_think_and_response("Рассуждения…\nЗадача\n    Описание")
    assert "Рассуждения" in t and "Задача" in f

def test_split_incomplete_think():
    # незакрытый тег: всё после него — think, финального ответа нет
    t, f = split_think_and_response("Оборванные рассуждения")
    assert "Оборванные" in t and f == ""
```

Отличие от исходного листинга Главы VI.5 (осознанное): реализация в репозитории
ищет содержимое между парными тегами через position-slices вместо одного
regex, корректно обрабатывает «только закрывающий тег» и второй галлюцинированный
`` внутри ответа (подрезает final до него); маркер `[INCOMPLETE]` —
уровень history/debug-логирования, а не парсера. Обёрнутые формы
`<atom>текст</atom>` (наблюдались у phi4-mini) правит `sanitize_text` (A2),
не эта функция.

Примечание для `client.py`: Qwen3 в chatml пишет рассуждения отдельным
сообщением с каналом `think`; на llama.cpp при `"think": true` они приходят в
`message.reasoning_content`, а не в `content`. Клиент обязан подавать в парсер
оба варианта (inline-теги и склейку `reasoning_content + content`).

## 5. Промпты остальных системных агентов

Каждый агент — изолированный вызов со своим коротким промптом; общие
правила те же: простой текст, никаких JSON, модель не знает об остальной
системе. Тексты фиксируются константами в модулях + снапшот-тестами.

| Агент | Модуль | Модель промпта (draft до Этапа 5) |
|-------|--------|-----------------------------------|
| ExecutorAgent | executor.py | «Выполни задачу, опираясь на контекст. Инструмент — строкой `tool args…`. Результат — после строки `РЕЗУЛЬТАТ:`.» |
| ReflectAgent | reflector.py | «Задача провалена. Вот задача, результат и ошибка. Ответь ОДНОЙ строкой: `retry` / `reframe: …` / `give_up: …`» |
| ResearchAgent | researcher.py | «Ответь на вопрос только по предоставленным фрагментам. Формат: вывод + список источников. Если данных нет — `НЕТ ДАННЫХ`.» |
| SummarizerAgent | history/orchestrator | «Сожми выводы детей в ≤N токенов, сохранив факты и числа. Без оценок.» |

Think/no_think выбирается системой по глубине (L0–L2 think, L3+ no_think;
для Executor — по наличию инструментов), не моделью (stack §5).

## 6. Чего в промптах быть НЕ должно (антипаттерны)

- JSON-схем и требований к формату машинного обмена (валидирует CPU);
- упоминаний инфраструктуры (Kanban/SQLite/RAG/BK-tree/другие агенты);
- категорий и спецсимволов (`> ! ? ⚛`) — удалены из-за путаницы малых моделей;
- длинных few-shot примеров (формат задаётся одной строкой шаблона);
- инструкций «думай/не думай» — режим управляется API-параметром.

## 7. Эволюция промпта (история решений, Глава VI.6)

| Версия | Размер | Что было | Почему отказались |
|---|---|---|---|
| v1 «с категориями» | ~800 токенов | инструкции `> ! ? ⚛` | модель путалась в символах; phi4-mini оборачивала `<atom>текст</atom>`; дублировала родителя |
| v2 «с примерами» | ~400 токенов | few-shot разбор «Создать REST API» | +300 токенов на каждый вызов; модель иногда копировала примеры дословно |
| **v3 финал** | **~50 токенов** | правила + формат отступом (см. §2) | — работает лучше: нет когнитивной нагрузки на категории, нечего копировать, формат интуитивен |

Экономия: (800 − 50) × 100 вызовов = **75 000 токенов** на типовой сессии.
Ключевой вывод для будущих правок: каждую строчку промпта нужно оправдать —
проверка покрытия/атомарности/типов задач лежит на CPU-слое, а не в тексте
инструкции (подробно — ADR 002, 003; data.md §1).

## 8. Открытые вопросы

- Итоговые тексты промптов Executor/Reflect/Research — принимаются на
  Этапе 5 вместе с тестами (product §8).
- Язык промптов: русский (текущий выбор — модель хорошо держит RU);
  для кодовых задач допускается смешанный вывод — sanitize не трогает латиницу.
