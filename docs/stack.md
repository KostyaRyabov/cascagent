## 1. Эволюция выбора inference-движка

Решение принималось итеративно. Каждое ограничение ниже — требование к
интерфейсу `client.py` / `cache_manager.py`, которое нельзя забыть при
смене бэкенда.

### 1.1 Попытка 1: Ollama

Начали с Ollama из-за простоты (`ollama pull qwen3:4b`). Проблемы:

1. Медленно из-за обвязки (HTTP overhead + модель-менеджер).
2. Нет ручного save/restore KV-кэша — только автоматический prefix cache.
3. Prefix caching нестабилен: инвалидация при смене параметров запроса.
4. Flash Attention зависит от версии → до 2x медленнее на длинном контексте.
5. Полноразмерный f16 KV-кэш → в 2 раза больше VRAM, чем нужно.

**Вывод:** хорош для прототипирования, не годится для production с
изолированными агентами — нам критичен управляемый кэш префиксов
(cpu-offload P8) и предсказуемая VRAM (принцип изоляции product.md).

### 1.2 Попытка 2: llama.cpp server

Плюсы: ручной save/restore через `/slots/N?action=save|restore`,
`--flash-attn`, квантованный KV-кэш (`--cache-type-k q8_0`), минимальный
HTTP overhead, OpenAI-совместимый API, стабильный prefix cache.

Минус: нет формата EXL2. **Qwen3 8B в Q4_K_M ≈ 5.5 GB → не влезает в
4 GB VRAM**; в бюджет проходит только Qwen3 4B (~3.0 GB) — ниже качество
декомпозиции. Это текущее зафиксированное решение (§4.1).

### 1.3 Попытка 3: ExLlamaV2 через TabbyAPI

Ключевое преимущество — **EXL2**: переменная битность по слоям (критичные
attention/embedding-слои 4 бита, остальные 2.5–3). **Qwen3 8B EXL2
4.0bpw ≈ 4.2 GB → 8B влезает в 4 GB VRAM вместе с KV-кэшем.**

Недостаток: нет эндпоинтов save/restore — кэш живёт только пока запущен
сервер (автоматический prefix cache).

### 1.4 Текущее решение vs кандидат на ревизию

| | Действующее (код) | Кандидат (обсуждается) |
|---|---|---|
| Движок | llama.cpp server | TabbyAPI (ExLlamaV2) |
| Модель | Qwen3 4B Q4_K_M (~3.0 GB) | Qwen3 8B EXL2 4.0bpw (~4.2 GB) |
| KV-кэш | авто prefix + ручной save/restore | только авто prefix |
| Аргументы «за» | управляемость кэша, скорость, простой деплой | качество рассуждений критичнее скорости; сервер перезапускается редко |
| Следствия для кода | — | `cache_manager.py` деградирует в no-op; think через `/no_think` вместо `"think": bool`; другие коды ошибок |

**Решение НЕ принято** (треacking — §7). До принятия код пишется под
llama.cpp; оба бэкенда закрыты абстракцией `client.chat(..., use_think)`
(§5.3), чтобы ревизия не трогала decomposer.

## 2. Сравнение inference-движков

| Характеристика | Ollama | llama.cpp | ExLlamaV2 (TabbyAPI) | KoboldCpp |
|---|---|---|---|---|
| Скорость (4B, tok/s) | 30–40 | **55–75** | 40–55 | 45–60 |
| 8B в 4 GB VRAM | ❌ | ❌ (только 4B) | ✅ EXL2 4.0bpw | ❌ |
| Prefix caching | ⚠️ нестабильный | ✅ авто + ручной | ✅ авто | ✅ авто |
| Ручной save/restore KV | ❌ | ✅ `/slots` | ❌ | ⚠️ частичный |
| Flash Attention | ⚠️ зависит от версии | ✅ | ✅ | ✅ |
| Квантованный KV-кэш | ❌ | ✅ q8_0/q4_0 | ✅ Q4/Q6 | ✅ |
| Draft model (speculative) | ❌ | ⚠️ базово | ✅ продвинутый | ✅ |
| OpenAI-совместимый API | ✅ | ✅ | ✅ | ❌ |
| Установка | 1 команда | cmake + build | Python env | 1 exe |
| Сообщество | большое | огромное | среднее | RP-ориентированное |

Примечание: draft model сознательно вне скоупа (AGENTS.md §9) — прирост
скорости не оправдывает усложнение и риск рассинхрона accept/reject.

## 3. Выбор модели

### 3.1 Критерии (по убыванию веса)

1. **Следование простому формату** (plain text с отступами, protocol v2) —
   малые модели нарушают JSON-схемы; у нас формат минимален именно поэтому.
2. **Качество декомпозиции** (reasoning) — главный продукт.
3. **Русский язык** — рабочий язык промптов и задач.
4. **Fit в 4 GB VRAM** вместе с KV-кэшем ctx ≥ 8192.
5. Управляемый **think-режим**.

### 3.2 Таблица кандидатов

| Модель | Формат / размер | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| **Qwen3 4B** | GGUF Q4_K_M ~3.0 GB | влезает с запасом под KV; русский; think; IFEval высокий | слабее 8B на сложных разбиениях | **текущий выбор (llama.cpp)** |
| **Qwen3 8B** | EXL2 4.0bpw ~4.2 GB | лучшее reasoning в бюджете | требует ExLlamaV2; нет ручного KV-кэша | кандидат на ревизию (§1.4) |
| phi4-mini 3.8B | ~2.8 GB | сильный reasoning | плохо следует формату (IFEval ~71) | ❌ формат критичен |
| Llama 3.2 3B | ~2.3 GB | быстрая | слабый русский, слабый IF | ❌ |
| Qwen2.5 7B | ~4.5 GB | хорошая модель | чуть слабее Qwen3 | ❌ |
| Mistral 7B | ~4.8 GB | популярна | уступает Qwen3 | ❌ |

### 3.3 Почему Qwen3, а не что-то ещё

- Одна из лучших open-weight моделей по instruction following и reasoning
  в своём классе; семейство нативно поддерживает Russian.
- Think-режим включается/выключается на уровне запроса (§5).
- Лицензия Apache 2.0 — совместима с лицензией проекта (см. также README
  проекта про выбор Apache 2.0: патентная защита, совместимость со стеком
  Qwen3/HuggingFace, привлекательность для контрибьюторов из компаний).

## 4. Конфигурация бэкенда

### 4.1 Действующая: llama.cpp server (Qwen3 4B)

```bash
./llama-server --model ~/models/qwen3-4b-q4_k_m.gguf \
  --host 127.0.0.1 --port 8080 --n-gpu-layers 999 --ctx-size 8192 \
  --flash-attn --cache-type-k q8_0 --cache-type-v q8_0 \
  --no-mmap --threads 6
```

### 4.2 Кандидатская: TabbyAPI + Qwen3 8B EXL2 (⚠️ пересмотреть AGENTS.md §3)

`config.yml`:

```yaml
model:
  model_dir: ./models/qwen3-8b-exl2   # квантование 4.0bpw (~4.2 GB)
  max_seq_len: 8192                   # ограничение контекста
  chunk_size: 2048                    # chunked prefill
  prompt_template: chatml             # чат-шаблон Qwen3

generation:
  temperature: 0.2                    # низкая — стабильность формата
  top_p: 0.9
  max_tokens: 4000

cache:
  mode: Q4                            # квантованный KV-кэш
  size: 8192
```

Запуск:

```bash
python start.py --model-dir ./models/qwen3-8b-exl2 \
  --host 127.0.0.1 --port 5000 --max-seq-len 8192 \
  --cache-mode Q4 --gpu-split "4"
```

### 4.3 Инварианты интерфейса (выполнимы на ЛЮБОМ бэкенде)

Требования к backend'у, которые обязывает соблюдать архитектура:

1. OpenAI-совместимый `/v1/chat/completions` (или тонкий адаптер в `client.py`).
2. **Стабильный префикс** работает как prefix-cache: SYSTEM_PROMPT — константа
   и стоит первым в запросе (protocol §2, cpu-offload P6/P8).
3. Возможность включить/выключить рассуждения на уровне запроса (§5).
4. Один инференс одновременно — single-flight очередь оркестратора
   (product.md §5); слотов/воркеров >1 не требуется.
5. `temperature=0.2` по умолчанию — воспроизводимость изолированных вызовов.
6. Никакого warmup и batch (AGENTS.md §9).

## 5. Управление think-режимом

### 5.1 Что это

Qwen3 генерирует блок рассуждений перед ответом. Он повышает качество, но
стоит 300–3000 токенов генерации на вызов.

### 5.2 Почему НЕ отключаем глобально

Без think малые модели резко деградируют: зацикливаются на тривиальных
задачах, дублируют родительскую задачу, генерируют бессмысленные
подзадачи. Качество декомпозиции — главный продукт, поэтому экономим
токены другими способами (минимальный промпт ~200 симв., CPU-алгоритмы),
а не отключением рассуждений на корневых узлах.

### 5.3 Механика и абстракция

| Глубина узла | Режим | Обоснование |
|---|---|---|
| L0–L2 | think | корневые/крупные разбиения — самая дорогая семантика |
| L3+ | no_think | мелкие узлы; экономия 300–3000 токенов THINK на вызов |

- llama.cpp: параметр запроса `"think": true|false`.
- TabbyAPI/Qwen3 chatml: soft-prompt `/no_think` в начале user-сообщения.

Абстракция `client.chat(messages, use_think: bool)` выбирает механику по
конфигу бэкенда; `decomposer.py` о ней ничего не знает (изоляция агентов).
Решение о режиме принимает CPU по таблице глубины (cpu-offload P7).

### 5.4 Парсинг THINK/FINAL

Разделение блоков — детерминированный CPU-сканер
(`parser.split_think_and_response`, cpu-offload A1): корректно обрабатываются
закрытый, незакрытый (модель обрезалась по max_tokens) и отсутствующий
`<think>`-блок. Оба блока логируются раздельно в debug.log (принцип
честного парсинга, AGENTS.md §8.3).

## 6. KV-кэш и бюджет токенов

### 6.1 Три уровня кэширования

| Уровень | Механизм | Модуль | Эффект |
|---|---|---|---|
| Системный промпт | prefix cache (авто) + save/restore `.bin` слотов | `cache_manager.py` (P8) | −~100 токенов префилла каждый вызов |
| Целые решения | exact-match кэш Kanban: hit ⇒ LLM не вызывается вообще | `kanban.py` (P1) | целый подцикл декомпозиции+выполнения |
| Похожие задачи | semantic recall top-3 в контекст | `semantic.py` (P2) | меньше ResearchAgent-вызовов |

На TabbyAPI уровень 1 деградирует до «авто prefix cache без save/restore»:
`cache_manager.py` обязан работать no-op'ом, если эндпоинты `/slots`
отсутствуют (probe при старте, логировать degraded mode).

### 6.2 Ожидаемое время одного вызова (capacity planning)

Оценки для 8B EXL2 на RTX 3050 4GB (~40 tok/s); для 4B Q4 — быстрее,
но чаще с retry. Честные цифры берём из `history.jsonl` (timings пишутся
на каждом вызове, cpu-offload A13).

| Фаза | Токены | Время @40 tok/s |
|---|---|---|
| THINK | 300–3000 | 7–75 с |
| FINAL | 100–500 | 2.5–12 с |
| **итого на вызов** | | **~10–90 с** |

Десять узлов декомпозиции ⇒ **десятки минут** машинного времени. Отсюда —
правило дисциплины: метрика `LLM-calls per root-task` должна расти только
вместе с реальной семантической работой (cpu-offload §0).

### 6.3 Бюджет контекста на вызов

ctx = 8192; целевой профиль одного вызова декомпозиции:
system ~100 + user (brief + enriched ≤ 1500 + siblings checklist ≤ 200) +
output budget (think + final ≤ 4000). Всё, что не влезает, сжимается на CPU
(Selective Context, P5) — не «отрезается хвост» и не уходит на дубль-вызов.

## 7. Открытые вопросы (трекинг ревизии стека)

1. **Переход на TabbyAPI + Qwen3 8B EXL2** — принять/отклонить до Этапа 2
   (`client.py` пишет интерфейс, менять потом дороже). Критерий: сравнить
   долю ложных атомов и degenerate-ответов на 4B vs 8B (бенчмарк из
   history.jsonl, таргет product.md §7 < 5%).
2. Если остаёмся на llama.cpp — нужен ли отдельный лёгкий эмбеддер для
   semantic memory (bge-small CPU) или pooled hidden states модели
   (product.md §8.3 — тот же открытый вопрос).
3. При переходе на TabbyAPI: обновить AGENTS.md §3 и architecture.md §6
   («llama.cpp, а не ExLlamaV2» — решение «менять нельзя» — придётся
   пересматривать осознанно).
4. Проверить поведение авто prefix cache TabbyAPI при чередовании
   different SYSTEM_PROMPT-free вызовов (Executor/Reflect) — не вытесняет ли
   декомпозиционный префикс; при необходимости — два slot'а.
