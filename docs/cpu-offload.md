# cascagent — Разделение нагрузки: CPU-слой vs GPU/LLM-вызовы

> Цель документа: зафиксировать, **какие алгоритмы и шаги выполняет CPU**,
> чтобы минимизировать число, длину и стоимость обращений к модели (GPU).
> Каждое правило здесь — архитектурное; отклонения обсуждаются через PR.
> Стоимость GPU-вызовов (движок, модель, think-режим, KV-кэш) —
> `docs/stack.md`; продуктовые сценарии и агенты — `docs/product.md`.

## 0. Бюджет инференса (почему это важно)

Qwen3 4B Q4_K_M на 4 GB VRAM: ~15–25 токенов/с генерация, префилл ~100–200
токенов/с. Один вызов декомпозиции с промптом ~300 токенов и ответом ~200
токенов ≈ 10–20 секунд. Дерево из 30 узлов × 2 (декомпозиция + выполнение) =
часы машинного времени. **Каждый перенос шага на CPU — прямая экономия минут
и риск OOM.** Поэтому правило №1: LLM вызывается только когда задача
неразрешима детерминированно.

Метрика дисциплины: **LLM-calls per root-task** должна расти только вместе с
реальной семантической работой, но не с рутиной (парсинг, валидация, поиск).

## 1. Принцип разделения

| Слой | Отвечает за | Стоимость | Детерминизм |
|------|-------------|-----------|-------------|
| **CPU** | структура, состояние, поиск, фильтрация, кэш, маршрутизация | мс–десятки мс | полный, тестируется без сети |
| **GPU/LLM** | только семантика: «разбей», «сделай», «проанализируй провал» | секунды | вероятностный, изолированные вызовы |

Критерий отнесения шага к CPU: *если для решения существует алгоритм или
таблица с приемлемым качеством — это CPU. LLM — последний резорт.*

## 2. Алгоритмы CPU (полный реестр)

### 2.1 До вызова модели (pre-call)

| # | Шаг | Алгоритм / структура | Модуль | Что экономит |
|---|-----|----------------------|--------|--------------|
| P1 | Кэш готовых решений | exact match `brief` → hash map; hit ⇒ задачи не отправляются модели вообще | `kanban.py` | целый подцикл декомпозиции+выполнения |
| P2 | Semantic recall | cosine по эмбеддингам numpy (top_k=3), пороги отсечки | `semantic.py` | ResearchAgent-вызовы: контекст найден без LLM |
| P3 | RAG по документации | BM25 (инвертированный индекс на SQLite FTS5) + vector merge, rank fusion | `rag.py` | вопросы «что такое X» внутри Executor |
| P4 | Выбор инструмента | BK-tree fuzzy search по описаниям манифестов, O(log n); Левенштейн+фонетика для опечаток (`fix_typo`) | `bk_tree.py` | MCP-схемы инструментов не попадают в промпт (−2000 токенов/вызов) |
| P5 | Сжатие контекста | Selective Context: удаление дублей предложений, low-infofuzz-фильтр, обрезка до budget | `enricher.py` | длина промпта ⇒ время префилла |
| P6 | Сборка промпта | pure-function конструктор фиксированной формы | `parser.build_user_prompt` | стабильный префикс ⇒ KV-кэш работает |
| P7 | Решение think/no_think | таблица по глубине: L0–L2 think, L3+ no_think | `decomposer.py` | no_think сокращает генерацию в разы на мелких узлах |
| P8 | Prefix KV-кэш | save/restore слотов llama.cpp `/slots/N?action=save|restore`; SYSTEM_PROMPT как неизменный префикс | `cache_manager.py` | повторный префилл system prompt (~100 токенов) каждый вызов |
| P9 | Нормализация запроса | strip/lowercase/unicode-NFKC перед любыми сравнениями | `detector.py` | ложные промахи кэша и ложные дубли |

### 2.2 После ответа модели (post-call)

| # | Шаг | Алгоритм | Модуль | Зачем не на LLM |
|---|-----|----------|--------|-----------------|
| A1 | Разделение THINK/FINAL | regex-сканер `<think>` (открытый/закрытый/оборванный блок) | `parser.split_think_and_response` | формат — не семантика |
| A2 | Санитайзинг строк | regex: буллеты, нумерация, markdown-обёртки, zero-width | `parser.sanitize_line` | модель не должна «думать» про чистоту вывода |
| A3 | Парсинг дерева | однопроходный скан отступов (O(n)) → Task[] | `parser.parse_decomposition` | детерминированная грамматика |
| A4 | Атомарность | точное сравнение `<atom>` / пустой ответ; без эвристик | `parser.is_atomic` | принципиальное решение AGENTS.md §8.1 |
| A5 | Degenerate-repeat | одна подзадача и similarity(brief_child, brief_parent) ≥ 0.75 ⇒ атом (protocol §3.6) | оркестратор + `detector.py` | спасает от бесконечных циклов передекомпозиции без нового вызова |
| A6 | Дедупликация детей | SequenceMatcher pairwise внутри списка, порог 0.75 | `detector.py` | лишние дети = лишние LLM-вызовы ниже по дереву |
| A7 | Антициклы | проверка кандидатов против цепочки предок→потомок (hash ancestor set) | `kanban.py` | защита от self-referential деревьев |
| A8 | Валидация структуры | brief непустой, description ≤ max_len, depth ≤ max_depth | `decomposer.py` | мусор ловится до записи в Kanban, без «почини вывод»-ретраев |
| A9 | Персистентность | UPSERT в SQLite, WAL-режим; JSONL append-only история | `kanban.py`, `history.py` | resume без повторного инференса после краша |

Схема таблиц (tasks/llm_calls/research_cache/semantic_memory), формат JSONL-записи
и конвенции WAL/backup — `docs/data.md` §3–4.
| A10 | Планирование исполнения | порядок детей = зависимости; FIFO single-flight очередь | оркестратор | модель не планирует расписание |
| A11 | Маршрутизация агентов | state machine (product.md §5): триггеры Reflect/Research/Summarizer | оркестратор | агент сам не решает, звать ли другого агента |
| A12 | Сборка результата | summarize_results(): конкатенация с budget; LLM-summarize — только если превышен бюджет | `executor.py` | типовой случай — чистый CPU |
| A13 | Метрики/отчёты | подсчёт токенов/времени/долей из history.jsonl; рендер дерева CLI | `cli.py` | наблюдаемость без инференса |

### 2.3 Ошибки и ретраи (тоже CPU-логика)

| Шаг | Правило |
|-----|---------|
| Таймаут вызова | client-side timeout → один retry того же промпта (стоимость удваивается, поэтому ровно один) |
| Пустой/битый вывод | НЕ отправляем «переделай формат» — парсер толерантен (A2/A3); если final пуст ⇒ атом (A4) |
| Сбой инструмента | код ошибки классифицируется таблицей (transient/fatal); transient ⇒ retry без LLM |
| Провал атома | 1 retry → ReflectAgent (единственный легальный новый LLM-вызов) → reframe → PENDING |

## 3. Что остаётся на GPU (исчерпывающий список!)

Ровно пять видов вызовов, все — isolated, короткий промпт, один HTTP-запрос:

1. **Декомпозиция** узла (DecomposerAgent) — единственный строго форматированный вывод.
2. **Выполнение атома** (ExecutorAgent) — когда атом требует генерации текста/кода;
   если атом маппится на инструмент (P4) — выполняется CPU-код, LLM не участвует вовсе.
3. **Рефлексия** над FAILED (ReflectAgent) — максимум 2 на задачу.
4. **Исследование** при пустом enrichment (ResearchAgent) — редко, по триггеру P2/P3.
5. **Суммаризация** при превышении budget (SummarizerAgent) — редкий fallback A12.

Запрещено просить модель: посчитать, отсортировать, найти дубли, проверить
формат, выбрать инструмент из каталога, составить расписание, сохранить/прочитать
состояние — всё это уже есть в §2.

## 4. Оценки сложности (почему CPU-путь дешевле)

| Операция | Сложность | Типичное время (16GB RAM laptop) |
|----------|-----------|----------------------------------|
| parse_decomposition (A3) | O(строк ответа) | < 1 мс |
| DuplicateDetector на список из k детей | O(k² · len) | k≤8: < 5 мс |
| BK-tree query (P4) | O(log n · d) | n=1000: < 1 мс |
| BM25 top-10 (P3) | O(query terms + postings) | < 20 мс |
| cosine recall 10k векторов (P2) | O(n · dim) numpy | < 50 мс |
| KV restore префикса (P8) | сетевой RPC | < 100 мс vs ~1 с префилла |
| **один LLM-вызов** | — | **10–20 с** |

Разница на два порядка: любой CPU-шаг оправдан, если он убирает хотя бы
10% вероятности лишнего вызова.

## 5. Правила для новых модулей (чеклист ревью)

1. Новый шаг прежде всего проверяется на «можно ли детерминированно» (§1 критерий).
2. Все CPU-функции — pure или с явным состоянием в SQLite/файле; тестируются без сети.
3. Пороговые константы (0.75, top_k, budgets) — именованные, в одном месте модуля.
4. Если CPU-алгоритм даёт неоднозначный результат — он НЕ угадывает: помечает
   задачу флагом `needs_llm=true` и передаёт управление оркестратору.
5. Любой новый вид LLM-вызова должен попасть в список §3 и получить триггер + бюджет.

## 6. Будущие оптимизации (зарегистрированы, не реализованы)

- **Speculative filtering**: дешёвый класcifier (logreg на эмбеддингах) решает,
  нужен ли вообще вызов Decomposer для узла (подозрение на атом по длине/лексике).
- **Result cache по хэшу (brief + context-hash)** вместо только exact-match P1.
- **Пакетная декомпозиция siblings** одним промптом при малом ctx — компромисс
  с изоляцией агентов; пока запрещена (§2.1 AGENTS.md).
- **Прогрев KV-префикса** одного SYSTEM_PROMPT отдельным холостым запросом —
  конфликтует с «no warmup» (AGENTS.md §9), принято не делать.
